# Правила работы с Z-Mod

## Репозитории и источники изменений

Все репозитории ниже принадлежат [ghzserg](https://github.com/ghzserg). Перед работой определить, где находится исходник, а не его копия или результат генерации.

| Репозиторий | Основная ветка | Назначение |
|---|---|---|
| [zmod](https://github.com/ghzserg/zmod) | `main` | Документация, архивы родных прошивок, wiki |
| [base](https://github.com/ghzserg/base) | `main` | Исходные конфиги, G-code-макросы, настройки и переводы |
| [z_ff5m](https://github.com/ghzserg/z_ff5m) | `1.7` | Общий код мода, AD5M / AD5M Pro |
| [z_ad5x](https://github.com/ghzserg/z_ad5x) | `1.7` | Дополнения AD5X к общему коду |
| [z_c5pro](https://github.com/ghzserg/z_c5pro) | `1.7` | Дополнения Creator 5 / Creator 5 Pro |
| [zmod_klipper](https://github.com/ghzserg/zmod_klipper) | `main` | Klipper для AD5M / AD5X |
| [zmod_klipper_c5](https://github.com/ghzserg/zmod_klipper_c5) | `main` | Klipper для C5 / C5 Pro |
| [guppyscreen_ff5m](https://github.com/ghzserg/guppyscreen_ff5m) | `main` | GuppyScreen для всех поддерживаемых принтеров |

| [zmod-spaghetti](https://github.com/ghzserg/zmod-spaghetti) | проверить | Локальный детектор дефектов печати |

Перед изменениями проверить актуальную основную ветку и локальный `AGENTS.md` целевого репозитория. Его специальные правила дополняют общие.

### Распространение изменений

`base → z_ff5m → z_ad5x → z_c5pro`

- Конфиги и макросы исправлять в `base`, в том числе специфичные для AD5X и C5/C5 Pro. Настройки и переводы менять в исходниках `base/csv/`. Генерация: `cd csv && bash Make.sh` в штатном расположении репозиториев; результат попадает в `../../translate/` относительно `csv`.
- Не исправлять вручную сгенерированные `translate/<язык>/*.cfg` в репозиториях принтеров. Сначала принять изменения в `base`, затем сгенерировать и распространить их по цепочке.
- Общий код, скрипты и файлы мода исправлять в `z_ff5m`, код только для AD5X — в `z_ad5x`, только для C5/C5 Pro — в `z_c5pro`. Переносить изменения в последующие репозитории с сохранением их специфики. Не создавать три независимых исправления одного общего файла.
- Код Klipper, GuppyScreen и веб-компонентов менять в соответствующем репозитории. Не переносить исправление между разными Klipper вслепую: проверить версии, конфигурацию MCU и особенности родной прошивки.
- Не запускать генерацию, распространение, выпуск релиза или слияние PR без поручения пользователя. Если поручен весь перенос, соблюдать порядок зависимостей и проверять результат на каждом этапе.

## Перед изменениями

- Работать от актуальной основной ветки, проверить открытые и принятые PR, зафиксировать базовый коммит. Перед отправкой повторно проверить актуальность базы.
- Делать только запрошенное. Если пользователь попросил анализ или diff, не менять репозиторий самостоятельно.
- Проверять реальное поведение по коду, конфигам и логам. Не переносить функции из других проектов только потому, что они существуют: сначала выяснить, решена ли задача в Z-Mod и есть ли практическая польза.
- Сохранять совместимость поддерживаемых моделей, родного экрана и режима без него, действующих версий Klipper, команд и пользовательских настроек.
- В текстах использовать **Z-Mod**. Не переименовывать ради этого пути, команды, переменные и URL.

## Код и diff

- Минимальный diff: без попутного рефакторинга, форматирования, переименований, обновления зависимостей и несвязанных файлов. Код простой и лаконичный; не выделять функции-обёртки ради пары строк.
- Не увеличивать без необходимости расход RAM, нагрузку CPU, число копирований, перерисовок, блокировок и фоновых задач.
- Не менять скорости, ускорения, тайминги, размеры буферов и штатные алгоритмы без обоснования и проверки. Не обходить аппаратные защиты и блокировки печати/паузы.
- Новые комментарии — только необходимые, на русском. Существующие комментарии без причины не переписывать.
- Сначала подготовить единый unified diff для всех затронутых файлов, проверить `git apply --check`, применить одним `git apply`. Затем `git diff --check`, тесты и один коммит на логическое изменение. Не отправлять пофайловые коммиты.
- Если инструмент не поддерживает применение общего патча или запуск команд, указать это явно; не выдавать просмотр кода за выполненные тесты.

## Тестирование и PR

- Проверять обычный сценарий, ошибки, восстановление состояния и совместимость затронутых моделей. Для аппаратных изменений использовать реальные замеры и безопасные тесты; не провоцировать столкновения и заклинивания.
- Запускать подходящие тесты и сборки. Для GuppyScreen: `make test`, `make test SANITIZE=1` и ThreadSanitizer согласно локальному `AGENTS.md` и актуальным целям Makefile.
- Для изменений работающего на принтере кода измерять память до/после на одном устройстве в одинаковых условиях: модель, коммиты, сценарий, `VmRSS`, `VmHWM`, `RssAnon`, `RssFile`, `VmData`, разница в КБ. Замеры на x86 не заменяют аппаратные. Если замеры или тесты недоступны, указать это в PR.
- Для UI — реальные скриншоты до/после в одинаковых условиях. В GuppyScreen указывать в описании PR `UI-Review: home, pid, system` (только изменённые экраны, до 8). Снимки для C5 Pro, AD5X и AD5M; подробности в локальном `AGENTS.md`. Не добавлять разовые картинки в исходники или отдельные ветки.
- Не создавать новый PR в том же репозитории, пока предыдущий PR агента не принят или не закрыт, если пользователь не попросил иначе. Доработки текущего PR вносить в его ветку. Не сливать PR самостоятельно без разрешения.
- В своих репозиториях названия коммитов, PR и комментарии — на русском; во внешних проектах — на английском.
- В ответе кратко указать результат, diff или ссылку на PR, фактически выполненные проверки и ограничения.

## Документация

- Документация находится в `zmod/docs/{ru,en,de,cs}/`. Русская версия основная: сначала исправить её, затем синхронизировать EN, DE и CS. Не оставлять разные описания одной функции.
- Писать кратко, естественно и понятно обычному пользователю. Для новых настроек указать назначение, значение по умолчанию, допустимые значения, модели и режимы работы. Не описывать внутренние команды как пользовательские.
- Изменения конфигов и макросов сопровождать обновлением соответствующих разделов документации. Параметры `[zmod_color]` описывать в руководстве C5/C5 Pro, глобальные параметры — в Global.
- В changelog текущей версии включать только новые функции и существенные исправления для пользователя. Сравнивать с предыдущим релизом и уже имеющимися записями, не выдавать прежнее поведение за новое. Не перечислять внутренний рефакторинг, временную диагностику и изменения CI. Не менять дату релиза без поручения.
- Изменения документации и changelog показывать единым diff; не переписывать старые версии без необходимости.
